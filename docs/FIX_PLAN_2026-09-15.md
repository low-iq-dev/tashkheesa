# Batch A — patient safety and the clock

Goes on the **existing** `fix/launch-gates-routing-revocation` branch, after Tasks 1–3 are committed and reviewed. Same files, same domain, no new worktree.

**A4 — Pre-acceptance data exposure.** Any doctor can currently open the pre-accept brief of any unassigned case, in any specialty, paid or not, and read the clinical question, history and medications. Fix so a doctor sees a pre-accept brief only when: the case is paid, it is offered to them or open to their specialty, and they are eligible to take it. Everything identifying — patient name, AI extractions, full history — stays hidden until they accept. A doctor assigned but not yet accepted sees the offer, not the patient.

**A5 — Unclaimable pool cases.** A pool case with no specialty can be accepted by any doctor holding the link. Fix so accepting checks specialty eligibility and payment status, not just that the case is unassigned.

**A6 — One acceptance deadline.** The deadline lives in `doctor_assignments.accept_by_at` and `orders.acceptance_deadline_at`, written and read by different code, so the dashboard and the case page disagree, broadcast gives 15 minutes where assignment gives 120, and one failure path leaves a case that never times out. Make one function the single source, write both columns from it, have every reader use the same one, and close the path that never expires.

**A7 — Retired wording in live copy.** `src/services/case_intake_pricing.js:157` tells patients to pick "fast-track". Replace with the correct tier name. Grep the whole repo for "fast track", "fast-track", "24h" and "72h" in patient-facing strings and fix all of them.

**A8 — Report PDF signature heading.** The PDF prints a "Doctor Signature / توقيع الطبيب" heading above a typed name and no signature. Change the heading to "Consultant / الاستشاري" with "Signed electronically · موقّع إلكترونياً" beneath. No image, no schema change.

# Batch B — the ledger and the report path

New branch `fix/earnings-ledger-and-report-service`, cut from `origin/main` **after batch A merges**. These two live in the same code path — report submission writes the earnings row — so they are one branch, not two.

**B1 — One earnings aggregation.** Eight separate SQL aggregations feed the doctor's earnings page, Command, and finance's "owed" figure, and they disagree. Build one function that returns a doctor's earnings for a period, and make every reader call it. No caller keeps its own SQL.

**B2 — Align the ledger with the policy.** Apply the decisions table above: reassigned earns 0 and the 10% token row goes; `paid` is stamped at month-end payout, not at submit; add-ons follow the same lifecycle; Cairo months by completion date everywhere. `earnings_writer.js` is no longer on the do-not-touch list — this batch is what it was being protected for.

**B3 — Correct the two production rows.** Both existing `doctor_earnings` rows are reassignment tokens that should be zero. Dry run inside `BEGIN … ROLLBACK`, show the output, Ziad runs the commit.

**B4 — Report submit becomes a service.** It is currently ~390 lines inside `handlePortalDoctorGenerateReport`, not idempotent — a double submit writes the records twice and re-notifies the patient — and it can mark a case completed when the status change itself fails. Lift it into a service the web route calls, make it idempotent on a submission key, and make completion atomic: either the report, the status and the earnings row all land, or none do.

**B5 — Update the policy doc.** One pass over `docs/PAYOUT_AND_URGENCY_POLICY.md` so it states the decisions above and contradicts itself nowhere.

# Batch C — doctor access and app prerequisites

New branch `feat/doctor-access-and-app-prereqs`, cut from `origin/main` after batch B merges. This is everything the doctor app needs that is portal-side.

**C1 — Sessions that survive a second device.** `users.refresh_token` and `users.push_token` are single slots, so signing in on the app logs the doctor out of the portal, and a second device silently steals the push token. Add a sessions table keyed by user and device, with per-device refresh and push tokens, revocation that still works, and the existing revocation stamp honoured.

**C2 — Doctors stop signing in through the patient door.** `POST /api/v1/auth/otp/verify` currently accepts doctors, issues a 30-day refresh token, does not check whether the doctor is deactivated or rejected, and silently creates a **patient** account when the phone matches nothing. Give doctors their own verify endpoint with the 12-hour refresh lifetime, the full account-state check the web portal already runs, and no account creation — an unknown phone is told to apply, not enrolled as a patient. Leave the patient endpoint's behaviour for patients unchanged.

**C3 — Decline.** There is no way for a doctor to decline a case; cases only leave a doctor by timing out, which is why acceptance windows burn. Add a decline action that records a reason, returns the case to the pool immediately, and re-offers it. Declining before acceptance earns nothing and costs nothing; this is not the same as a reassignment after acceptance.

**C4 — Two small columns.** An appearance preference on the doctor's profile (dark or daylight, following them across devices), and a per-doctor phrase library table for the report composer's saved phrases. Both are additive migrations.

**C5 — RLS on the three uncovered tables.** `deleted_users`, `email_delivery_events`, `email_suppressions`. Default-deny like the other 64. Low urgency, no clinical data, but it closes the set.
