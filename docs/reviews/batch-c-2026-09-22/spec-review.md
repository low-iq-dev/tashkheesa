## Findings

### S1 — MAJOR — Per-phone OTP budget doubled across the two doors (in the reviewed commit)
The commit duplicates the per-phone limiter **instances** in `src/routes/api/doctor_auth.js:53-77` ("same shape, separate counters", header :28-30) instead of sharing them with `src/routes/api/auth.js:44-71`. express-rate-limit's MemoryStore is per-instance, so one phone number gets 3 SMS sends + independent 60s cooldown *per door* — 6 sends / 15 min total, doubling exactly the SMS-bombing/Twilio-cost ceiling AUDIT-P0-8 exists to cap, and 10 verify attempts against a 6-digit code instead of 5. This is the precise concern of review focus (d). **Already fixed in the uncommitted worktree** (`src/middleware/otp_phone_limits.js` + both routers rewired to the shared instances) — that fix must be committed, and the committed `docs/BATCH_C_PROGRESS.md` must not claim "SHARED" until it is (S11).

### S2 — MAJOR — Account erasure leaves `user_sessions` rows behind (in the reviewed commit)
The commit's `src/services/account_deletion.js` does not sweep `user_sessions`. An erased account's rows retain refresh JWTs, Expo push tokens, device ids and human device names — PII-adjacent residue in a PDPL-posture erasure flow (`deleted_users` is precisely the tombstone table C5 locks down). The dangling refresh tokens are not live credentials (both refresh paths re-SELECT the user and fail), but "an erasure erases." **Already fixed in the uncommitted worktree** (`account_deletion.js:118-130`, optional-table listed so pre-110 environments still delete cleanly) — must be committed.

### S3 — MINOR — A refresh token rotated away by pre-C1 code stays redeemable through its seeded session row
Transition edge on C1's rotation contract. The 110 seed copies `users.refresh_token` as of the migration snapshot into `sess-legacy-<uid>`. If, in the zero-downtime deploy window, the *old* code then rotates that token (writes T1 to the mirror), the seeded row still holds T0 with `revoked_at IS NULL` — and post-cutover `findLiveByToken(T0)` (`api/auth.js:280`, `user_sessions.js:79-85`) honours it. Pre-C1 semantics said a rotated-away token is dead; during the transition, both T0 (via the seeded row) and T1 (via adoption) refresh successfully, each becoming its own "device". Bounded: only the token that was current at snapshot and rotated during the deploy window; both strings were held by the same device stream; T0 dies at JWT expiry. No action strictly required, but worth a line in the report/runbook; a cheap hardening would be for `adoptLegacyToken` to revoke the user's other still-live `device_id='legacy'` rows holding a *different* token.

### S4 — MINOR — sid logout no longer clears the push-token mirror (push can follow a signed-out device during the transition)
Pre-C1 logout cleared `users.push_token` (AUDIT-APP-H6/H7). Post-C1, a logout carrying a `sid` calls only `revokeById` (`api/auth.js:733-735`), which clears the refresh mirror but never `users.push_token`. A device whose push token lives in the mirror (registered by a pre-C1 build, or via the sid-less fallback in `profile.js`/`admin.js` push registration) then signs in with new code and logs out — the mirror token survives, and `_liveTokensForUser` (`src/middleware/push.js`) unions it back in, so the signed-out device keeps receiving case/report pushes until it re-registers, the token dies (`DeviceNotRegistered` cleanup), or the user hits `DELETE /profile/push-token`. Transition-window only, but it re-opens the exact H6 complaint on a medical account. Suggested fix: in the `sid` logout branch, also `UPDATE users SET push_token = NULL WHERE id = $1 AND push_token = <this session's push_token or the mirror value when the user has no other live session>` — or simply clear the mirror when the revoked session was the user's last live one.

### S5 — MINOR — Decline can write an SLA event through the half-done-state repair path
`markReassignedOnReassignment`'s idempotency branch (`earnings_writer.js:901-913`) deliberately **falls through and INSERTs a `doctor_sla_events` row** when the main row is `status='reassigned'` but no event exists (crash-half-done or pre-109 flip not covered by the backfill). Sequence: doctor A accepted → reassigned away with the event write lost → case later re-offered to A (`ASSIGNED`, not yet re-accepted, so the row stays 'reassigned') → A *declines* → the decline route calls reassignCase → the repair path records an SLA event (with reason `doctor_declined:<cat>`) for what the spec says must never write one. Extremely narrow (requires a prior torn write AND the same doctor getting the case back AND declining), and the recorded event arguably repairs a *previous* hand-off, not the decline — but the reason string it stores is the decline's, which would mislead an operator reading `doctor_sla_events`. Cheapest fix: in the fall-through, keep the row's existing `reassignment_reason` for the event rather than the caller's decline reason; or skip the repair when the incoming reason starts with `doctor_declined:`.

### S6 — MINOR — Superadmin push-recipient count ignores per-device sessions (in the reviewed commit)
`src/services/ops_push.js` in the commit still counts recipients from `users.push_token` alone, while the send path (`push.js notifySuperadmins`) now fans out over the sessions UNION — a Command device registered post-C1 (token on its session row only) would be pushed to but counted as zero, defeating the "zero is worth recording" telemetry. **Already fixed in the uncommitted worktree** (UNION count matching the send path) — must be committed.

### S7 — MINOR — Live session rows never expire and are never cleaned up
Sign-ins without a `deviceId` accumulate one live row each (`createSession` only replaces rows for a matching `(user, device_id)`, `user_sessions.js:61-67`); seeded legacy rows whose tokens went stale on old-code rotation stay `revoked_at IS NULL` forever. A row whose JWT has expired is unredeemable (verify fails first), so this is not a credential risk, but live-but-dead rows (a) inflate the push fan-out candidate set (mitigated by `DeviceNotRegistered` cleanup, `push.js`), and (b) will make any future "your devices" UI show ghosts. The spec's created/last-seen timestamps exist precisely to support a sweep; none is scheduled. Suggested follow-up (separate ticket): a worker that revokes rows with `last_seen_at` older than the refresh TTL.

### S8 — NOTE — Migration 112 covers a fourth table the spec did not ask for
`doctor_sla_events` (Batch B's 109 missed the post-070 RLS opt-in) rides along in 112, justified by a live `pg_class` check ("exactly these 4 uncovered"). Right thing to do and same defect class — but it is a deviation from the letter of C5 ("two additive migrations… RLS enabled on deleted_users, email_delivery_events, email_suppressions"), recorded here so the extra scope is a decision, not a surprise. The live-check claim was not independently re-verified by this review.

### S9 — NOTE — Rollback keeps only the most recent device signed in
C1's mirror maintenance means a rollback to pre-C1 code restores exactly pre-C1 behaviour: the single slot holds whichever device last signed in or rotated, and every *other* device opened under C1 dies at its next refresh. This is the best a single-slot mirror can do and is documented (`user_sessions.js:29-32`), but "nobody is signed out by the deploy" does not extend to "nobody is signed out by a rollback" once users have actually used multi-device — worth one sentence in the deploy notes.

### S10 — NOTE — Patient refresh now enforces `tokens_valid_after` (behaviour change for patients, sanctioned by the spec)
Pre-commit, a patient's 30-day refresh token survived a password change (the stamp was only consulted in `requireJWT`). Post-commit it is revoked at next refresh (`api/auth.js:308-313`). This is a real patient-visible change under review focus (e), but the spec's C1 line "the existing revocation stamp (users.tokens_valid_after) still honoured" sanctions it, and it closes a genuine stolen-device hole. Every other patient-door change checked (register/login/otp/logout/push/forgot/reset): envelope and codes unchanged for patients; the only refusals added are for doctors (`DOCTOR_LOGIN_REQUIRED` at otp/verify, `REFRESH_REVOKED` role partition at refresh), both mandated by C2.

### S11 — NOTE — Committed progress ledger lags the code on two claims
The worktree `docs/BATCH_C_PROGRESS.md` states "OTP per-phone limiters SHARED across both doors" and "…/deletion rewired" — true only of the **uncommitted** changes, false of commit `2b58b8c81`. The committed doc version makes neither claim (and also lacks the "no longer authoritative from this deploy" sentence C1's report requirement asks for — the worktree version carries it). Once the worktree fixes are committed together with the doc, this resolves itself; flagged so doc and code land in the same commit.

### S12 — NOTE — `ACCOUNT_REJECTED` ordering depends on `pending_approval` being cleared
`doctorStateAnswer` checks `pending_approval === true` before the rejected branch (`doctor_auth.js:96-108`). The reject service sets `pending_approval = false` in the same transaction (`admin_doctor_reject.js:73`), so the normal flow is correct — but any legacy/hand-edited row with `pending_approval = true` AND `rejection_reason` set would answer `ACCOUNT_PENDING_APPROVAL` instead of `ACCOUNT_REJECTED`. Cosmetic (both are 403 dead-ends with support copy); no action needed unless such rows exist in prod.

### S13 — NOTE — Minor surface observations, no action required
(a) `POST /doctor/auth/logout` accepts any role's valid JWT and revokes that token's own `sid` — harmless (self-revocation only), just not doctor-scoped. (b) The shared per-IP `authLimiter` instance covers `/auth`, `/admin/auth` and `/doctor/auth` together (`api_v1.js:94,107,118`), so one IP's 20/15min budget spans all three doors — pre-existing pattern from the admin mount, unchanged by this batch. (c) `doctor_phrases.doctor_id` and `user_sessions.user_id` carry no FK — consistent with the schema's house style (109's `doctor_sla_events` has none either). (d) Sign-out does not invalidate the device's outstanding 15-minute *access* token — pre-existing contract (revocation stamp is per-user), unchanged.
